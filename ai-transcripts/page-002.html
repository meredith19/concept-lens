def parse(css, media=None, out=None):
    """Return list of (media, selector, {prop: value})."""
    if out is None: out = []
    css = strip_comments(css)
    i, n = 0, len(css)
    while i < n:
        brace = css.find('{', i)
        if brace == -1: break
        prelude = css[i:brace].strip()
        # find matching close brace
        depth, j = 1, brace + 1
        while j < n and depth:
            if css[j] == '{': depth += 1
            elif css[j] == '}': depth -= 1
            j += 1
        body = css[brace+1:j-1]
        if prelude.startswith('@media'):
            parse(body, media=re.sub(r'\s+', '', prelude), out=out)

# Only fact-level equivalence is authored; concept relationships are derived

Concept Lens has a deliberate two-layer design that the user has stated directly, and it governs
how the model is allowed to grow.

**Authored:** semantic mappings between individual facts, and only ever with the type
`SAME_MEANING`. A mapping says that one fact in one source system states the same thing as one
fact in another, each in its own vocabulary.

**Derived:** every relationship between whole concepts — equivalence, containment, partial
overlap, disjointness. These are computed by comparing which of two concepts' facts are joined by
confirmed mappings. They are never stored and never authored by a person.

The practical consequence is that `MappingType` should stay at `SAME_MEANING` alone. Do not add
`IMPLIES` or other weaker relationship types to `MappingType`. When something looks like
implication or containment between two concepts, the correct modelling is a fact-level
`SAME_MEANING` mapping plus derivation at the concept level: Shipped and Delivered, for example,
share the "left the fulfillment center" fact by equivalence, and the fact that Delivered is the
stronger concept falls out of Delivered having an additional unmatched fact.

# Seed YAML is read once at startup and never written back

Concept Lens keeps its initial demo data in YAML under `src/main/resources/demo/` —
`concepts.yml` simulating concepts published by independently owned source systems, and
`mappings.yml` holding the semantic mappings Concept Lens itself owns. The user has been explicit
about how these files are meant to behave, and it is easy to get wrong.

These files are **startup seed data only**. They are loaded into in-memory repositories when the
application boots and are never read again, and nothing the application does at runtime writes
back to them. If a future task involves adding, editing or removing a mapping, the change belongs
in the in-memory repository alone; do not "helpfully" persist it by rewriting the YAML.

The two kinds of data behave differently once loaded:

- **Concepts are read-only in the application.** They are owned and published by their source
  systems, so Concept Lens offers no way to create or modify them.
- **Mappings are mutable at runtime**, with add and remove operations against the in-memory
  mapping repository. Concept Lens owns mappings, so this is the one thing it can change.

A restart therefore resets mappings to the seeded state, and that is the accepted behaviour for
now rather than a bug — real persistence is a deliberate later step. Do not introduce a database,
a file writer, or any other persistence mechanism to "fix" it unless the user asks.
